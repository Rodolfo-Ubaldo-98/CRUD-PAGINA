2. Codificación de archivos

El proyecto requiere utilizar UTF-8 de forma consistente en archivos de código, configuración, respuestas web y textos de la aplicación. Esta regla es especialmente importante para conservar correctamente los caracteres españoles, como á, é, í, ó, ú, ñ, ¿ y ¡.

Cualquier modificación futura deberá conservar la codificación existente compatible con UTF-8 y evitar conversiones que produzcan caracteres corruptos o ilegibles.

3. Reglas de auditoría en SQL Server

3.1 Triggers de auditoría de Persona

Las operaciones sobre la tabla Persona deben conservar el mecanismo de auditoría mediante los siguientes triggers:

  • TR_Persona_Insert
  • TR_Persona_Update
  • TR_Persona_Delete

No se debe sustituir este mecanismo por otra solución sin revisar previamente el diseño existente y justificar el cambio.

3.2 Identificadores generados

Después de insertar un registro, debe utilizarse SCOPE_IDENTITY() para recuperar el identificador generado. No debe utilizarse @@IDENTITY, porque podría devolver el identificador creado por una operación interna de un trigger u otra operación secundaria.

SELECT SCOPE_IDENTITY();

3.3 Restricción sobre OUTPUT

No debe utilizarse OUTPUT sin INTO en operaciones INSERT o UPDATE sobre Persona. Antes de modificar estas operaciones deben revisarse los procedimientos almacenados, las consultas y los triggers relacionados.

3.4 Contexto de sesión para operaciones sensibles

Antes de cualquier operación que cambie el estatus, la aprobación o las credenciales, se debe ejecutar sp_set_session_context con el valor IdUsuarioApp. La configuración y la operación posterior deben ejecutarse en la misma conexión de base de datos.

EXEC sys.sp_set_session_context
    @key = N'IdUsuarioApp',
    @value = @IdUsuarioApp;

El contexto de sesión no se comparte automáticamente entre conexiones distintas. Por ese motivo, no sería correcto establecerlo en una conexión y efectuar la actualización en otra.

4. Gestión de System.IdentityModel.Tokens.Jwt

El paquete System.IdentityModel.Tokens.Jwt, versión 8.23.0, se instaló manualmente únicamente en el proyecto Registro.Servicio.

Si otro proyecto necesita utilizarlo, primero deben indicarse:

  • El proyecto que requiere el paquete.
  • El archivo que utilizará sus tipos o APIs.
  • El motivo técnico de la dependencia.

No se debe instalar el paquete automáticamente en todos los proyectos. Si aparecen conflictos de ensamblados, deben resolverse mediante bindingRedirects en Web.config, revisando las versiones efectivamente utilizadas.
